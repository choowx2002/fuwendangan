# 可能缺失的功能 · Missing Features

> 按优先级分组。依据代码证据（存在/缺失），并对照「Beta 风险清单」逐项检查。标注：Beta 必须（阻塞）/ 建议 Beta 前 / 可延后。

## 高优先级（Beta 前建议处理）

### M01 多设备玩家数据同步（未实现）
- 证据：`docs/player-data-sync.md` 为「设计定稿，待实施」；代码中无 `user_sync_*` 表、无同步引擎。
- 为什么重要：玩家数据（收藏/卡组/借还/清单）仅存本机，换机/重装靠手动备份。
- 是否 Beta 必须：否（可用备份/导出流程替代）。
- 可否延后：可延后，但 Beta 必须向用户明确「数据在本机，换设备靠备份恢复」。

### M02 自动备份 / 备份提醒（未实现）
- 证据：备份仅 `settings → 备份数据库` 手动触发；无启动备份、无周期备份、无到期提醒。
- 为什么重要：Beta 期间若用户误点「恢复」或遇到数据库损坏，无自动兜底即**可能丢失全部收藏数据**。
- 是否 Beta 必须：**是（阻塞级风险）**。最小方案：启动时若距上次备份超过 N 天提示一次，并增加「一键导出完整数据包（db + 收藏 CSV + 卡组 JSON）」。
- 可否延后：不可延后，先做提示/一键导出。

### M03 备份文件 schema 校验（缺失）
- 证据：`restoreDatabase` 直接 `copyFile` 覆盖，无版本/schema 校验；恢复旧库或错误文件可能启动后崩溃或数据混乱。
- 是否 Beta 必须：**是**。至少在恢复前读取备份头/校验 db 可打开、表存在；Beta 说明「恢复只保证同版本」。
- 可否延后：不可延后（属数据安全）。

### M04 购买清单「已满足/已购」与库存的实时同步（部分实现）
- 证据：`savePurchaseListBatch` 已把 bought 写回收藏、`refreshPurchaseListFromDeck` 可刷新；但清单条目状态（`qty_to_buy`/`status`）在用户**直接改收藏**后不会自动重算，需手动保存/刷新才更新；心愿单条目也不会因收藏已足而自动置 acquired。
- 为什么重要：状态不同步会造成「显示缺卡但实际已有」或重复购买。
- 是否 Beta 必须：否（有手动刷新兜底）。Beta 说明「手动编辑收藏后需刷新清单」即可。
- 可否延后：可延后，但要写进 Beta 须知。

## 中优先级（Beta 期间可补，建议尽早）

### M05 卡柜抽屉卡片移除无确认（缺失）
- 证据：`locker/[lockerId]/[sectionId]/edit/+page.svelte` 的 `handleQuickDec`(L189)、`removeSelected`(L275–297)、`removeCard`(L306–308) 均直接调 `removeSectionCard`，无 `ask()`/`confirmAction()`。
- 为什么重要：误点即删除柜内记录（无撤销），其余模块删除均有确认，此处是唯一未确认的删除路径。
- 是否 Beta 必须：建议修复（低成本），若来不及至少 Beta 须知提示。
- 可否延后：可延后，但强烈建议 Beta 前补上。

### M06 老用户启动不自动检查内容更新（行为缺口）
- 证据：`+layout.svelte` 仅在 `version` 表为空时触发同步；已有数据的用户每次启动不会自动拉新卡，需手动去设置页「检查更新」。
- 为什么重要：Beta 期间发布新系列卡，老玩家会一直看不到新卡，容易误报「卡库没更新」。
- 是否 Beta 必须：建议。最小方案：启动时后台静默检查（在线且非计量网络下），发现新版本时给一次确认框（沿用现有 ask 流程）。
- 可否延后：可延后，但 Beta 须知要写「新卡需要去设置→检查更新」。

### M07 到期借还的系统通知（未实现）
- 证据：仅应用内 `getLoanDueSummary` 角标/汇总；无定时本地通知（notification 插件仅在卡图下载进度使用）。
- 为什么重要：借出核心价值之一是「记得催还」；应用没开时无提醒。
- 是否 Beta 必须：否。可否延后：可延后。

### M08 部分导出/加载失败的静默处理（部分实现）
- 证据：deck 详情页 PDF/图片/QR 导出失败多为 `console.error` 无 toast；`/decks/[deckid]/records` 与 logs 页 `loadData()` 无 try/catch；首页两处空 catch；`/rules` 仅 console.error。
- 为什么重要：用户点击导出无反馈，体验像「坏了」。
- 是否 Beta 必须：建议把「导出失败 toast」补齐（低成本）；Beta 可接受，但需在收集反馈时留意。
- 可否延后：可延后。

### M09 借还 / 联系人 CSV 导出（未实现）
- 证据：CSV 覆盖收藏/心愿/清单/卡柜/卡组；无 loans/contacts 导出。
- 为什么重要：与整库备份互补的轻量迁移；缺卡场景已覆盖，此项非核心。
- 是否 Beta 必须：否。可否延后：可延后。

### M10 应用内反馈表单 / 崩溃上报（未实现）
- 证据：唯一反馈入口是设置页飞书文档链接（`openUrl`）；日志仅本地。
- 为什么重要：Beta 收集问题效率低（用户要复制日志 → 打开链接 → 粘贴）。
- 是否 Beta 必须：否（提供反馈模板 + 日志导出说明即可）。可否延后：可延后。

## 低优先级（可延后）

- 证据：`/rules` 无空态；`/collection/[seriesCode]` 网格无空态。
- 是否 Beta 必须：否。可否延后：延后。

### M13 设置项（settings.json）不随备份/恢复（缺口）

## Beta 风险清单专项核查

| 风险点 | 结论 | 证据 |
| --- | --- | --- |
| 是否可能丢失用户数据 | ⚠️ 有风险可控 | 有手动备份/恢复 + CSV/JSON 导出；但无自动备份、恢复无 schema 校验（M02/M03）；误删均有确认（除卡柜卡片 M05） |
| 是否没有备份/导出 | 有备份与导出 | DB 备份、完整收藏 CSV、卡组 JSON、心愿单/清单/卡柜 CSV、缺卡 TXT/CSV |
| 是否没有删除确认 | 基本都有确认 | 全部核心删除均有 `ask()/confirmAction()`；唯一例外：卡柜卡片移除（M05） |
| 是否有重复插入购买清单问题 | 已防住 | `UNIQUE(list_id, card_no, card_no_extend, language_pref, finish_pref)` + upsert；批次保存事务化；bought 写回后归零防重复 |
| 是否借出归还没有影响可用库存 | 已实现 | `available = owned − 生效借出 + 生效借入`（active/overdue 生效），归还即恢复（`checkDeckOwnership`/`getActiveLoanQty`） |
| 是否心愿单/购买清单/库存状态不同步 | 部分实现 | 写回路径齐全（acquired→收藏、bought→收藏、借入对账）；但外部改收藏后需手动刷新（M04） |
| 是否没有处理空数据 | 大部分已处理 | `EmptyState` 覆盖收藏/心愿/借还/清单/卡组等；缺 `/rules`、系列页（M12） |
| 是否没有错误提示 | 大部分有 | toast + 对话框广泛使用；部分导出/加载路径静默（M08） |
| 是否没有用户反馈渠道 | 有但弱 | 设置页飞书文档链接（唯一入口），无应用内表单（M10） |
| 是否有隐私问题 | 风险低 | Local-first、无埋点、凭据不落库；注意：备份 .db 含联系人私密信息，需提示用户妥善保管（F173） |
